# Autonomous First-Party Company-Career Discovery Implementation Plan

Status: approved architecture; Checkpoint A implementation only in the current batch.

## Goal and boundary

Batch 3.5 extends the existing Batch 3 job-discovery path to approved first-party employer career surfaces. It does not create a space, mechanical, AI, or software feature. All role families enter the same provider-safe query, normalization, deduplication, frozen evaluation, persistence, Tailored feed, and Explore feed path.

The only editable source authority is `config/approved-job-sources.json`. It contains a broad, reviewable 41-company seed and a smaller verified active cohort. Unverified entries remain disabled. Greenhouse and Lever remain the only provider connectors currently authorized. First-party mechanisms are separately audited and never become automatic authorization for an unsupported ATS.

Out of scope: LinkedIn, Indeed, Glassdoor, search-result scraping, arbitrary crawling, authenticated candidate sessions, CAPTCHA or anti-bot circumvention, applications, extensions, paid feeds, evaluator/scoring changes, locked benchmark execution, and the Batch 4 Jobs UI.

## Unified architecture

```text
version-controlled company registry
  -> one audited source plan per company
  -> robots and URL safety policy
  -> provider delegation OR approved first-party listing discovery
  -> static detail retrieval and structured/deterministic extraction
  -> optional audited browser retrieval
  -> existing Batch 3 connector/retrieval boundary
  -> normalization, deduplication, provenance, frozen evaluation
  -> SQLite persistence, Tailored/Explore feeds, existing APIs
```

The source plan is staged, not a single extraction strategy:

```python
class SourceMechanism(StrEnum):
    GREENHOUSE = "greenhouse"
    LEVER = "lever"
    FIRST_PARTY = "first_party"
    DEFERRED = "deferred"

class ListingDiscoveryMode(StrEnum):
    PROVIDER = "provider"
    SITEMAP = "sitemap"
    STATIC_INDEX = "static_index"
    BROWSER_INDEX = "browser_index"
    DIRECT_DETAIL_URLS = "direct_detail_urls"

class PageFetchMode(StrEnum):
    STATIC_HTTP = "static_http"
    BROWSER = "browser"

class DetailExtractionMode(StrEnum):
    JSON_LD_THEN_HTML = "json_ld_then_html"
    JSON_LD_ONLY = "json_ld_only"
    DETERMINISTIC_HTML = "deterministic_html"
```

The Python 3.11 implementation uses `TypeVar` and `Generic` where generic fields are needed; it does not use PEP 695 syntax.

One company has one audited execution plan per refresh. A provider-backed official page may prove a provider relationship, but it cannot also be independently crawled in the same refresh. A first-party plan may use sitemap/index discovery, static detail retrieval, JSON-LD, deterministic HTML fallback, and an explicitly audited browser fallback as one plan.

## Registry authority and contracts

`config/approved-job-sources.json` is the sole editable authority. The existing legacy provider registry remains a read-compatible lower-level view during migration. `load_approved_source_registry()` is the production composition boundary: it loads the company registry, loads legacy provider configuration, applies freshness, and rejects board collisions before exposing either view. `load_company_source_registry()` and `validate_legacy_compatibility()` remain lower-level testable helpers; `adapt_legacy_sources()` represents old Greenhouse/Lever entries in the new typed shape without audit approval or an audit date. Later retrieval code must compile the authoritative company entries into one runtime source per company.

The source plan contains separate `mechanism`, listing discovery mode, detail fetch mode, detail extraction mode, typed provider connector configuration, sitemap/index/direct URLs, navigation/redirect/resource/API hosts, allowed path patterns, browser and page limits, audit version, and audit date. `ExtractionProfileSpec` is declarative only: link patterns, attributes, selectors, labeled fields, pagination patterns, and canonicalization policy. It admits no imports, executable code, scripts, unrestricted XPath, credentials, cookies, or authorization headers.

Registry validation rejects duplicate source IDs, company IDs, canonical domains, provider-board IDs, wildcard/IP-literal hosts, credentials and secret-like configuration, enabled deferred/stale/rejected entries, invalid mode combinations, and browser plans without audited hosts and positive limits.

`compute_registry_plan_hash()` canonicalizes stable identity, host/path, URL, provider, browser, plan, and profile-reference data using sorted compact JSON and SHA-256. It excludes display notes, priority, cadence, and enabled state. `compute_extraction_profile_hash()` canonicalizes only the source ID and declarative extraction profile; changing selectors, attributes, labeled fields, pagination patterns, or canonicalization changes it, while prose and operational metadata do not.

## Safe HTTP and robots boundary

Checkpoint A uses direct dependencies `httpx>=0.28.1,<0.29` and `httpcore>=1.0.9,<1.1`. `UrlAccessPolicy` validates HTTPS, no credentials, exact approved hosts and paths, and DNS results. `ValidatedDestination` records host, validated public IP, port, and scheme. `ValidatingAsyncNetworkBackend` resolves and blocks loopback, private, link-local, reserved, multicast, unspecified, carrier-grade NAT, documentation/test, metadata-service, and mixed public/blocked answers before delegating a TCP connection to the validated IP. The HTTP core origin remains the hostname, so TLS SNI, certificate validation, and the Host header retain the original employer host. `PinnedAsyncHTTPTransport` uses a manual redirect policy, no environment proxies, bounded pool, and zero retries by default. `SafeHttpClient` revalidates every redirect and enforces timeout, response-size, content-type, and redirect limits without persisting bodies.

Static HTTP fully prevents non-HTTPS, credentialed, unapproved-host/path, blocked-DNS, mixed-answer, proxy-environment, and unvalidated-redirect requests within this client. Each new connection resolves and validates its destination before connecting to that validated IP; the HTTP origin remains the approved hostname for Host/SNI/certificate checks. Browser navigation and every browser subresource require separate approved host lists and redirect validation; no browser is added in Checkpoint A.

Robots parsing implements exact user-agent then wildcard groups, longest matching rule, equal-length Allow precedence, wildcard/terminal anchor handling, percent-decoding for matching, a 500 KiB cap, and a 24-hour cache. 404/410 permits access without a policy; 401/403 returns deferred access review; 5xx, timeout, DNS failure, or an unparseable policy disallows that refresh. Robots failures never silently become permission.

Conditional validators may reuse URL membership after 304 only when source ID, audit version, registry-plan hash, and extraction-profile hash all match. A changed identity forces an unconditional bounded request. A failed unconditional request may preserve historical validators but cannot mark historical URLs newly seen or successfully verified. Raw HTML and response bodies are never persisted.

## Audit-time detection

`detect_source_strategy()` is deterministic and runs only during an explicit audit or stale-audit review. It recognizes Greenhouse, Lever, JobPosting JSON-LD, Workday, iCIMS, SmartRecruiters, Ashby, Workable, Jobvite, SuccessFactors, custom first-party, and unknown. It may inspect only approved audit-entry responses and signals such as canonical host, approved redirects, official links, script/source URLs, form actions, and structured-data URLs. It produces evidence and a deferred result for unsupported ATS platforms; it never mutates registry configuration, authorizes a provider, calls authenticated endpoints, or redetects on every normal refresh.

## Lifecycle and deduplication decisions for later checkpoints

Normalize substantive fields before fingerprinting: canonical title, normalized company, description text, normalized location, work arrangement, employment type, posted date, updated date, requisition/external ID, and authoritative application URL. Exclude raw HTML, analytics scripts, generated IDs, timestamps caused only by page chrome, and unrelated markup. Exact source-qualified IDs and authoritative application URLs are required for aliases. Fuzzy company/title similarity alone never merges jobs.

Each job tracks first seen, last seen, last successfully verified, last changed, content fingerprint, availability, source health, and alias evidence. One failed request or one omitted flaky index record does not close a job. A conservative future rule is: close only after an authoritative 404/410, or after three consecutive successful complete membership checks omit the job; a source outage resets neither membership nor verification. A later successful check reopens a previously closed posting, and changed application URLs retain the old URL as provenance while the new first-party URL becomes authoritative.

Ordinary tests are offline. The only permitted unrelated full-suite exception is `tests/test_health.py::test_api_plan_and_document_use_reconciled_composition` returning HTTP 503 when exact DOCX page counting is unavailable. No rendering, DOCX, health, resume, or cover-letter code may be changed to hide it. The locked benchmark never runs.

Static gates are Ruff on changed Python files, compileall on changed source packages, and strict mypy with `--strict --follow-imports=silent` on newly created Checkpoint A modules and direct typed boundaries. The repository’s known pre-existing strict-mypy baseline is not an implementation gate; no new errors may be introduced in changed modules.

## Dependencies and risks

HTTPX 0.28.1 is the existing HTTP client and supplies the request/response API; httpcore 1.0.9 is made an explicit direct dependency because the pinned network backend must connect to a validated IP while preserving the HTTP origin. The transport isolates its private HTTPX/httpcore backend and exception-mapping imports in `safe_http.py`; the local HTTP/TLS tests are the compatibility gate before widening either dependency range. The standard library supplies URL parsing, IP validation, hashing, JSON, regex, and robots parsing. No HTML parser, browser, or new ATS dependency is added in Checkpoint A. The custom backend requires careful version pinning and offline fake-backend tests; runtime resolver/OS behavior remains a deployment risk. Robots policy changes, employer redirects, stale audits, provider board migrations, missing IDs/dates, and first-party JavaScript changes remain explicit structured outcomes rather than guessed metadata.
